# 08 · 返修与回复审稿人

**适用范围：** 本文件完整流程用于相应的完整修订／返修项目；指定句段、文档或仅建议的任务按 [SKILL §0、§7](../SKILL.md) 决定调用范围、必要继承、复查与停止，不自动扩大成整稿或全包。用户明确不检查时只做授权修改并标明未验证，不把未执行记通过。

回复信的读者是编辑和审稿人。他们要在最短时间内确认三件事：

- 每条意见都处理了；
- 处理是实质性的；
- 声称的修改在稿子里确实存在。

## 1 · 流程

### 1.1 拆意见

运行 `response_lint.py 意见.docx --to-matrix 07_response/comments_matrix.csv`，然后逐条核对拆分是否正确。

### 1.2 逐条分析

结果写进处理表。每条意见回答四个问题。

**审稿人真正质疑的是什么？** 从以下几类中判断：

- 研究问题或理论依据；
- 设计与方法；
- 数据质量、样本量或统计推断；
- 稳健性、可重复性或外部效度；
- 解释与结论边界；
- 与文献的关系；
- 结构、语言、透明度或报告规范。

**问题出在稿子的哪里？** 定位到段落、表、图、代码或文献。

**属于哪种情况？**

1. 研究确实有不足；
2. 已有证据，但没写清；
3. 分析或报告有可修正的问题；
4. 审稿人误解了，原因是表达不清；
5. 建议有价值，但不完全适用；
6. 材料不足，需要核实。

**怎么处理？** 接受、部分接受、通过澄清回应、有依据地不接受，或暂时无法确定。

### 1.3 需要新增分析时，先过九问

1. 具体要解决什么问题？
2. 现有结果为什么不够？
3. 数据和方法能否支持？
4. 有没有更简单、更直接的办法？
5. 统计假设、模型选择、多重检验能否妥善处理？
6. 结果可能怎样影响原结论？
7. 是否与已有分析重复？
8. 会不会造成选择性报告或过度分析？
9. 收益是否抵得上增加的复杂度和篇幅？

据此决定：实施、作为可选的稳健性分析、改用其他证据，或不实施，并写明理由。结果不显著或削弱了原有解释，同样如实报告，并判断它对结论的影响。

### 1.4 改稿

先改稿，再写信。改动要保持全文一致（见 07），并用 revision_diff 留下证据。回应要融入论文：审稿人问过不等于读者需要，新增内容的去处按读者决定（07 §10）。

### 1.5 写信，然后检查

写信见 §2，检查见 §6。

## 2 · 回复信的结构

结构参考了真实回复样例；按本刊和意见调整，不把样例当通用模板。作者有以往的回复信时，它是最近的近邻：版式、致谢方式、回复标记先照它，和目标刊要求冲突时按目标刊。

**开头一段**依次写：

- 一句感谢；
- 主要修改，两到四条，每条一句，带数字或位置；
- 结构变化：新增的表、补充材料、文献数；
- 位置约定：页码取干净稿正文页脚印出的页码（不用投稿系统 PDF 的 “Page X of Y”，后者常含扉页会多一页）、修订如何标示、意见如何编号。

**意见顺序**：编辑的意见在前，然后按审稿人顺序排列。

**每条意见的格式**：

1. 审稿人原话，完整引用；
2. **Response** / **Answer**；
3. **位置**：写明具体位置，可以单列一行 Changes，也可以嵌在回复句里，全信一种写法。页码行号来自约定的最终文件；未分页时用章节/段落锚点并标待更新。

**版式（可选）**：意见与回答在视觉上可区分——例如意见灰底斜体、Answer:/Response: 加粗（可配深色字）。不要整段黄高亮，也不在信里描述样式本身（不写“见蓝色文字”）。期刊或作者已有版式时先照已有的。

**Response 的写作顺序**：

1. 明确回应合理关切；若前提不成立，礼貌说明依据，不虚假认错；
2. 给出证据：新分析的数字和表号、已有数据的重新呈现，或文献；
3. 说明改了什么；
4. 说明没做什么、为什么，以及替代做法。

**确有未在逐条回复中说明的实质改动时**加一节"Additional changes made by the authors"，逐条列出修改过程中自己发现并改正的、读者会受影响的错误及其位置。这既体现诚信，也能避免审稿人复审时发现未说明的改动。标签、排版这类不影响理解的小修不列，列了反而刻意。

## 3 · 写法

- **直接**：第一句就进入实质。默认致谢只在信首说一次。作者以往的信是逐条致谢时（登记进 expectations.json），用同一句朴素公式，只按意见类型换成 comment / suggestion / question（或中文「意见」「建议」「问题」），不轮换 thank / appreciate / grateful 等同义词，不给致谢附理由（because… / which led us…），不用恭维词（valuable、insightful）；编辑的事务性要求不用致谢。
- **本条自足**：审稿人可能只读自己那几条。不写“见对 Reviewer 1 第 3 条的回复”，把要点写在本条，或指向稿件的位置。
- **只写审稿人要核对的**：做了什么、结果、位置。不逐句复述正文，不叙述段落结构（“该段最后写了……”），不把补充表的内容搬进来。
- **定位与引用都写全**：写 Page 12, lines 10–21，不写 p. 12；页码取正文页脚，不用系统 PDF 的 “Page X of Y”；全信粒度一致。文献写法与正文的文内引用一致，不写 new reference 55。
- **具体**：每条"已修改"都给出位置，以及改后的文字或数字。
- **诚实**：审稿人说得对，就直接承认。问题无法用现有数据解决时，说明边界和相应的处理，例如写进局限、补充一张表，不要用复杂措辞掩盖。
- **礼貌地不同意**：给出证据和替代做法，一次说清，不要重复三遍。可以写"我们理解这一点可能源于第 2.3 节表述不清，已改写为……"，不要写"审稿人误解了"。
- **不过度顺从**：审稿人的要求会引入错误时（例如按小样本亚组下结论），解释原因，并给出替代做法。编辑会读这封信。
- **审稿人之间有冲突**：明说冲突，给出你们的取舍和理由，请编辑裁决。
- **预判追问**：每条重要回复写完后，想一想审稿人看了最可能再问什么。能当场补上的，就补上。

### 3.1 · 局部润色仍须核对主张与指称

即使只澄清几句，也要对照相关权威材料核对改写前后是否等义；不因未加引号或脚本退出 0 而免核。按主文件 Local 规则限制范围，不自动重审全稿。

**硬检查（发现问题须裁决）：**

1. **观察与推断分开。** 未在题名摘要中匹配，只支持该观察；“因此仅匹配 Keywords Plus”需要实际字段证据及排除其他来源的依据。未报告不等于不存在，未识别不等于没有使用。
2. **简化保留有效分支。** 核对纳入规则中的“或”、例外、限定和适用对象；包括设计上可解释模型的规则，不能改成只接受事后解释方法。
3. **不凭润色增加分类或历史。** more mature 是比较判断，formerly Theme A 声称更名历史，都需要材料支持；展示顺序本身不证明成熟度或演进。
4. **敏感性分析说清操作与假设。** 分开交代补入、剔除的数量和方向，识别未编码记录，并说明上下界怎样构造；例如逐指标将补入的未编码记录分别视为全属／全不属。必须与实际计算一致，不用 every possible coding 代替假设，不无据声称全局最坏界。
5. **本条可理解且复述准确。** the second of the two explanations 要复述承重选项；criterion (b) 要交代规则含义。允许同句解释、前文已定义、保留编号或表号；不要为了通俗删掉规则分支。

**判断提示：** 先交代机制或结论，再给内部术语；是否补解释取决于本条已有信息，不给所有术语重复定义。材料足够时自行最小修正；只有事实缺失且影响实质结论时才向作者询问。

`response_lint` 的 R-PTR／R-RULE 仅提示英文选项与规则编号候选；常见紧邻解释可跳过，复杂前文定义须人工裁决。检查作者开头与答复，不把审稿意见或引号内旧句当新主张。无命中不等于语义正确；字段来源、资格规则和上下界仍须对照来源。

## 4 · 要避免的写法

以下例子都来自真实的回复信。

| 写法 | 问题 | 改为 |
|---|---|---|
| 每条都以"We thank / We appreciate … valuable suggestion"开头，或轮换同义词并附理由 | 套话；轮换显得刻意；恭维词稀释实质 | 默认信首致谢一次；作者要逐条致谢时，固定一句朴素公式，只换 comment/suggestion/question |
| "We would like to clarify that our study is X rather than Y" | 先辩解，没有承认审稿人背后的关切 | 先承认关切中合理的部分，再说明本研究能做什么、不能做什么 |
| "We have revised the manuscript accordingly / thoroughly revised" | 没有位置，也没有内容 | 给出位置和改后的文字 |
| 回复里写"我们新加了：'……'"，正文里却找不到这段 | 复审时会被发现 | 用 `response_lint --manuscript` 核对 |
| 页码按投稿系统 PDF 的 “Page X of Y”，或按旧版估算 | 常比正文页脚多一页；定位错误 | 以干净稿正文页脚印码为准；每次改稿后按当前稿重算 |
| 用"将在未来研究中……"代替这次本可以做的修改 | 回避问题 | 能做的这次就做；做不了的说明原因 |

## 5 · 第二轮及以后

- 只回应仍未解决的问题和新提出的问题，编号沿用上一轮。
- 审稿人把"是否需要补充分析"交给编辑决定时，有两种做法：说明为什么现有证据足以支持收窄后的结论；或者提出可行的替代办法，例如在局限中写明推广范围、在补充材料中加一项可做的分析。不要过度承诺。
- 复审时，审稿人会核对上一轮声称的修改。任何"声称改了、其实没改"的地方，都是新的严重问题。

## 6 · 检查与交付

**检查**：运行 `response_lint.py 回复信 --manuscript 修改稿 --comments N`，确认：

- 条数一致；
- 每条都有回复和位置；
- 没有未填的占位符；
- 没有堆叠的套话；
- 引用的新文字在修改稿中确实存在。

**交付**：

- 回复信；
- 修订稿（真实的 Word 修订）和纯净稿；
- 修改依据与差异记录；
- 补充分析包（确有必要时）：脚本、运行说明、验证记录；
- 给作者的"需要你们决定的事"清单：需要补数据或确认事实的回复、建议礼貌不采纳的意见、审稿人之间的冲突、待填的数字。

**验证程度要分开写**，分为四档：

- 在真实数据上运行，并核对了关键结果；
- 在模拟数据上测试过；
- 只做了静态检查；
- 无法验证。

不能把"脚本能运行"等同于"统计方法正确"。

## 7 · 容易漏掉的返修核对

总意见和每条子问题保留稳定 ID；一个 Comment 的三个要求不能只答一个。检查 reviewer/editor 不同回复之间的事实与范围：总样本外部验证不能写成某亚组验证；回复的分析样本、结果和正文保持一致。行号起点不得大于终点，重排后更新全部定位。正文新引文同步文献表，回复专用文献独立列清。审稿人没有同意的地方不写成共识。

退出 0 仅代表脚本识别范围内无候选；人工核完整意见矩阵、范围一致性和实质回答。显示修订颜色不等于真实 Word 修订；期刊若只需高亮按要求提供，说明何种标记。不得把批注、作者身份或旧回复混入匿名稿。

## 8 · 返修的最后两步

逐条回复写完、双向核对完：先按 [07](07_revision_protocol.md) §9 做全稿清扫（审稿意见只是问题的一部分样本），再按 07 §10 做融入审查（回应加多了同样是问题）。这两步改动的地方也写进修改清单，影响读者的列入“作者额外修改”。
