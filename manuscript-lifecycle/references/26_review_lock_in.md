# 26 · 审查的框架锁定：先审尺子、范式外审稿与拒收预演

一次投稿包做了两轮隔离审查，全部脚本检查都“通过”了，作者第一眼看出的问题却一个也没被拦下：引用太少、结果小标题像结论、结果节有结论式表达、表格里留着程序代码。复盘发现，问题不在审稿人不够多，而在审查被锁在了同一个框架里：

- 审稿人拿本技能的章节契约当尺子；契约里恰好写着“结果小标题说出发现”，于是所有人一致放行。尺子错了，隔离再多也只会一致地错。
- 审稿人只拿到 Markdown 正文：表格、图注和补充材料没有进入审查，补充表里的内部代码没有任何人看见。
- 论证审稿人读完稿件约一分钟后交回“0 条发现”，没有说明查了什么，汇总脚本照单全收。
- 13 组裁决里 11 组用同一句模板理由关闭；“锚点原句改动”就算解决。
- 每项检查各自通过，被合并成一个“可交付”。

用拉卡托斯的话说，这是只修保护带：每轮只改被点到的句子，从不追问稿件的写法框架本身对不对。还有一层：早先为减少误报加的豁免（否定句一律不算因果、不算解释）在另一边制造了漏报。下面的做法从框架外面给审查加检验。

## 1. 先审尺子（二阶检查）

审查开始前，主对话列出这一轮用到的标准并标明来源：用户明确要求（expectations.json）、目标刊作者须知、近邻论文实测（bench_profile、benchmark_decisions.csv），还是本技能的默认。只来自本技能默认的标准，与近邻论文或用户要求冲突时，以后者为准，并记进决策登记。尺子没有外部证据时，审查结论只能写“按本技能默认”，不能写“符合同类论文”。

## 2. 异质的审稿人，而不是换了名字的同一个人

同一模型的子代理共享盲点。有用的是输入不同、尺子不同：

| 角色 | 拿什么当尺子 | 补哪个盲区 |
|---|---|---|
| reviewer_argument、cold_reader 等 | 稿件与章节契约 | 职能错位、推理断裂 |
| reviewer_outsider | 近邻论文同节原文与用户要求；不读本技能的 references 与 agents | 技能规则本身的偏差 |
| reviewer_coverage | 覆盖表与检索 | 该引而未引 |
| reviewer_display | 渲染页、原图与显示名登记 | 表图里读者看不懂的标签 |

所有角色的稿件输入都是 `review_pack.py` 生成的完整审查包（正文、表、图注、补充材料、图片清单）。

## 3. 关口默认关闭

- 零发现不是通过：没有覆盖证明（查了哪些节、做了哪些检查、至少两条“看过且没问题”的原文样例）就退回（review_merge validate）。覆盖证明只能提高空审的成本，不能保证认真：样例要看是否真来自审查的重点位置。
- 裁决逐组写改动证据；同一理由重复三次即报错；major 采纳要 change_evidence（review_merge check）。下一轮按问题类别全稿复查，不只看上一轮的锚点。
- 没能运行的检查、提取不了的图内文字、没有覆盖表的投稿稿，都不算通过。
- 用户指出过的问题登记进 expectations.json，之后每轮都是硬回归项：其他检查全绿也不能抵消，更不能改记为“个人偏好”。
- 每条豁免都配一个反例测试：为减少误报而放过的写法，要证明它没有放过真问题。

## 4. 拒收预演

交付前做一次：假设作者看完不满意，最可能的五个理由是什么？逐条去稿件里找证据，能修的修，不能修的写进作者说明。特别查三类审稿人常看不见、作者一眼就看见的问题：参考文献的规模与覆盖；各节读起来像不像正常的投稿论文（标题、段落职能、语气）；读者看到的每一个标签。

预演写成 `reject_drill.md`（模板在 assets/templates/）：默认探针逐条判定（摘要末句、摘要堆否定与校正、引言首段立题、引言末段分析菜单、方法流水账、主文表型、整篇报告腔、补充材料堆积；返修与修订另有 RJ11：读得出审稿或改稿过程），另加至少两条本稿特有的理由；每行写稿中位置、状态与证据，“仍在”的写进作者说明。genre_gate RD1–RD5 核对，投稿阶段缺它即阻断（[27](27_genre_and_placement.md)）。

## 5. 批判之后要能建造

每条批判都带可执行的改向：结果句给去向（方法、讨论或删去），内部 ID 给显示名草稿与定义出处，覆盖缺口给检索式。只拆不建的审查和只修不拆的审查同样让稿件停在原地。建设与批判分阶段交替：起草只建，审查只拆，裁决把两边合起来并写清取舍。同样，不要矫枉过正：结果节里短的统计限定、复现所需的方法细节、必要的披露，都不能因为“像结论”或“像过程”被一并删掉。

## 6. 什么时候停

两轮复查没有新的重大问题、核心维度不退步、登记的用户要求全部满足，才谈得上收敛。继续质疑的代价超过收益时可以停，但要在作者说明里写明还剩什么没查（例如没有外部专家审稿、没有在作者的 Word 里实际排版）。

## 7. 裁决的两条补充

- **把“文字主张是否有支持”与“实现细节是否可知”分开裁决。**审稿人指出“稿件说解码不依赖参考电极，但没有交代保证这一点的处理”时，缺实现细节不能成为不采纳的理由：稿件的那句话本身没有支持，应改写措辞；实现细节另列作者待办。
- **外部审查导入为一轮审查。**其他模型或人的审查意见，按发现逐组写进 review/roundN/adjudication.csv（锚点取原稿原句），逐组裁决采纳、部分采纳或不采纳并写理由；改稿后运行 review_merge check 核对采纳组的锚点已不在新稿中。外部审查找到而本流程漏掉的问题，要回答“哪一站本该拦住它、为什么没有”，修流程而不是只修这一处。
