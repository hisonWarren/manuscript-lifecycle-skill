# 19 · 多代理：什么时候用、怎么隔离、怎么汇总

## 1. 为什么需要，为什么不是默认

本 skill 记录的最顽固失败是写稿者看不见自己的问题：同一上下文会为已有选择找理由，只改被点到的句子，读过作者解释后就按解释去读稿件。
隔离上下文的审稿人看不到作者的理由、自评和上一轮结论，只能从稿件出发，这是消除锚定最直接的办法。
另一个用处是规模：60–100 条引文核对、30 条以上审稿意见、20 篇以上对标文献，放在一个上下文里会挤掉主线。

但同一模型的多个子代理会共享盲点，一致意见不等于专家共识；子代理越多，成本越高，同时改稿还会互相覆盖。所以：
审稿人只报告、不改稿；只有主对话一个人改稿；能用脚本或原文核对的，以脚本和原文为准。

## 2. 什么时候用

| 情境 | 用 | 默认配置 |
|---|---|---|
| 完整初稿完成、每轮大改后（D/R 模式审查步骤） | 是 | cold_reader + reviewer_methods + reviewer_argument + reviewer_language，并行；有表图时加 reviewer_display |
| 投稿前 | 是 | 上述四个 + citation_checker（只核承重引文，每个子代理 ≤10 条）+ reviewer_coverage + reviewer_display + reviewer_outsider（[26](26_review_lock_in.md)） |
| 收到审稿意见，意见 ≥10 条或审稿人 ≥2 位 | 是 | 每位审稿人一个 response_drafter；主对话统一改稿后，再派一个未见回复草稿的 reviewer_argument 复查 |
| 改一段、润一句、回答具体问题 | 否 | 直接做 |
| 稿件不完整、只有大纲 | 否 | 先写；冷读者对不完整稿件没有意义 |

每轮通常覆盖 4 个角色，投稿前最多 8 个；按可用并发槽分批派发，每个角色仍使用独立上下文，不让同一个执行者接着扮演另一个角色。一般 2 轮，最多 3 轮。只有工具允许隔离子代理输入时，才能称为隔离审查；继承主对话全部历史的子代理不满足这里的盲审条件。

## 3. 输入与隔离

| 角色 | 给 | 不给 |
|---|---|---|
| cold_reader | 稿件 | 故事卡、修改说明、任何审查结果 |
| reviewer_methods | 稿件、预注册/分析计划、补充材料 | 作者对分析选择的辩护、结果台账的分档理由、其他审稿人意见 |
| reviewer_argument | 稿件、02 章节职能契约 | 修改说明、故事卡、其他审稿人意见 |
| reviewer_language | 稿件、领域包或对标文献、skill 脚本 | 其他审稿人意见 |
| citation_checker | 一批"原句 + 引文 + 可得原文" | 作者对引用的辩护、其他批次结果 |
| response_drafter | 一位审稿人的完整原始意见、稿件、数据出处 | 其他审稿人的意见与草稿 |
| reviewer_coverage | 审查包、覆盖表、检索工具与作者的文献夹 | 作者对引用数量的辩护、引文核对结论、其他审稿人意见 |
| reviewer_display | 审查包、渲染页或原图、显示名登记表、display_terms 报告 | 作者对命名的辩护、其他审稿人意见 |
| reviewer_outsider | 审查包、近邻论文同节原文、expectations.json | 本技能的 references、agents 与 exemplars，故事卡，其他审稿人意见 |

所有角色的“稿件”都是 `review_pack.py` 生成的审查包（正文、表、图注、补充材料与图片清单），manuscript_sha256 填审查包的指纹。只给 Markdown 正文会漏审表格。

派发时给简报文件路径（agents/<角色>.md）和材料路径，让子代理自己读；主对话不必把简报内容读进自己的上下文。
每个子代理把结果写到 `review/round_N/<角色>.json`，在返回消息里只报告文件路径和发现条数。

## 4. 汇总、裁决、核对

1. 校验：`python scripts/review_merge.py validate --manuscript ms.md review/round1/*.json`。稿件指纹不符的整份退回；零发现却没有覆盖证明（查了哪些节、做了哪些检查、至少两条原文样例）的整份退回；
   major 发现的引文在稿件中找不到（子代理"引用"了不存在的句子）即退回。
2. 合并：`python scripts/review_merge.py merge --manuscript ms.md --out review/round1/adjudication.csv --report review/round1/summary.md review/round1/*.json`。
   按位置聚类，多人共同指出的排前面；不同审稿人的判断并列保留，不投票。
3. 裁决：主对话逐组填 decision（采纳 / 不采纳 / 暂缓）与 reason，依据证据而不是人数。每组 reason 写具体改动与解决方式，采纳的 major 填 change_evidence；同一句模板理由重复 3 次以上，check 报错。语言类发现转入 language_plan 逐处裁决。
   冷读者的 restatement 与故事卡对照，不一致处本身就是主线问题。
4. 改稿：只由主对话改。改完运行 `review_merge.py check --adjudication … --after ms_v2.md`：每组都有裁决，采纳的锚点原文已改动。
5. 下一轮：派新的子代理审查修改稿，不给上一轮的发现；复查对象是问题类别，不只是上一轮的锚点，同类写法全稿再查一遍；合并时加 `--previous 上一轮裁决表`，标出"仍在"与"新出现"。
   收敛判断沿用 SKILL.md §5：没有未解决的重大问题，且连续两轮没有新出现的重大问题。

引文核对的结果写入 verify_evidence.py 的 citation 记录（review 字段由人完成）；返修草稿进入意见矩阵，改稿后用 response_lint.py 与 revision_diff.py 双向核对。

## 5. 没有子代理工具时

先在工作记录中写明“子代理：无”，再选一种审查方式：

1. **新对话**（真正的上下文隔离）：请用户在新对话中粘贴角色简报（agents/<角色>.md）和稿件，把输出的 JSON 带回，同样用 review_merge.py 校验与汇总。
2. **单代理自查**（随时可做）：在本对话中直接核对稿件与来源，交付说明标明“非独立自查”。不要依次换角色名称来模拟上下文隔离，也不要在同一回答里一口气扮演四个审稿人再自己汇总：那是一份评论换了四个标题，没有隔离效果。

无论哪种方式，脚本检查照常运行；交付说明写明实际用了哪种审查、是否独立。

## 6. 边界与评估

- 包内自动测试覆盖机械部分：发现文件格式、锚点核对、聚类（锚点句相同而节名写法不同，如 results 与 results/discussion、global，也并为一组）、裁决落实与轮次对比（evals/test_domains_agents.py、evals/test_independent_regressions.py）。
- 子代理审查是否比单代理找到更多真实问题，需要在支持子代理的环境中做行为评估：
  用带已知问题的稿件（evals/behavior_cases/ 或植入问题的已发表论文），比较单代理自查与多代理审查的检出率和误报率，
  并记录成本。先固定输入和问题清单，给单代理与多代理同一稿件；各角色只能看其契约允许的资料，明确不同角色的信息差异。
  按问题类别去重计算检出率，额外发现逐条核实，区分真实遗漏、误报和待核事项。记录各角色耗时、总调用数、排队时间；拿不到 token 或费用就明确未测。
- 现有证据只有一份合成短稿（植入 12 类已知问题）：单代理自查 16 条发现，四个隔离角色共 33 条（合为 15 组），都覆盖全部 12 类；
  角色审查没有新增检出，重复意见更多，各角色耗时合计约为单代理的 3 倍。长稿、真实稿件和更隐蔽的问题还没有数据，
  在此之前既不能说多代理更准确，也不能说它没有价值。
- 审稿人意见一致时仍要按证据裁决；审稿人都没发现，不等于没有问题。


## 7. 选材审查（起草之前）

构想与去向登记写完（S3）之后、起草之前，派 `agents/reviewer_selection.md` 审选材方案。给它主张清单、搁置清单、去向登记、调研综述与语料、材料清点；不给作者对贡献的自述与故事卡。它从两个方向审：放进论文的是否都服务主张、经得起追问；没放的里面，有没有与主张相关却因为结果不好被藏起来的（[29](29_selection_and_survey.md)）。没有子代理时按 §5 降级，并在交付说明里标明“非独立”。

## 5b. 单代理自查的七项结构

没有隔离上下文时，“非独立自查”最容易退化成格式核对：一次实测里自查只查了重复句与否定收尾，漏掉了引言预测的前提错误、中介量纲错误和概括位置的强化。自查记录（04_audit/self_review.md）必须逐项写下面七节，每节给出查到的位置或“未见问题”的覆盖证明（station_check ST7 核对节名）：

1. **前提审计**：引言里每条“如果 H，那么应当观察到 O”——O 是 H 的必要条件吗？H 成立而 O 不出现的路径有哪些？
2. **推断链**：每条主张从数据到结论的每一步，写下最强的替代解释，以及稿件是否回应。
3. **概括位置漂移**：题目、摘要、讨论首末段、结论的每句，与结果节的对应句比较强度（显著性之差、分离、来源措辞）。
4. **派生量复算**：所有派生量按公式与单位复算（derivation_check）。
5. **文献概括核对**：每句对前人研究的概括，回到被概括论文的全文核对。
6. **惯例、语步与质感偏离**：deviation_register 列出的偏离（惯例、关键段语步、文本质感、词汇）是否都已裁决；改的是原因，不是指标。
7. **冷读**：只读摘要、图注和结果，标出未定义就出现的指代（“四个时间窗”“N1 窗”）与读者会卡住的地方。

条件允许时仍应请用户在新对话中运行 agents/ 里的隔离角色；外部（其他模型或人）的审查意见按 26 §7 作为一轮审查导入并逐组裁决。
